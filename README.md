# オペレーションハブ（kintai-checker）

総務・経理まわりの業務をまとめて回す Flask Web アプリ。
**2026-08-14 に「勤怠突合チェッカー」から改名**（フォルダ名・exe名・起動方法は従来のまま）。

出発点は勤怠の突合（jinjer の勤怠 CSV と各部署の勤務表（Excel/PDF/画像）を突き合わせて
差分を検出）で、現在は 経費チェック・経理（freee仕訳）・社労士CSV・
スケジュールアップロード・健康診断HPM・メール下書き の各モードを持つ。

---

## 🎯 このツールの使用用途

> **対象：全部署。jinjer に登録された勤怠と、取引先・現場から届く勤務表の「ズレ」を見つけるためのツールです。**

### 何のためのツールか

各部署では、**jinjer に打刻・登録された勤怠**と、**取引先や派遣先から届く勤務表（請求勤怠）**の
2 つの記録が存在します。この 2 つは本来一致するはずですが、打刻漏れ・入力ミス・転記ミスなどで
食い違うことがあります。食い違ったまま請求・給与に進むと、**過払い／過少請求や給与計算ミス**に
つながります。

このツールは、その **2 つの記録を自動で突き合わせ（突合）、差分だけを抜き出して一覧化**します。
目視で 1 件ずつ照合していた作業を、ファイルをアップロードするだけで数分に短縮します。

### こんなときに使う

- 月次の締め前に、**jinjer の勤怠と各社の勤務表が合っているか**を確認したいとき
- 取引先から届いた勤務表（**Excel / PDF / 画像 / スキャン**）の時刻を、jinjer と照合したいとき
- **シフト記号（B・●・明 など）で書かれた勤務表**を時刻に変換して突合したいとき
- jinjer に勤怠はあるのに **勤務表が未提出の人**を洗い出したいとき
- jinjer に存在しないシフト記号について、**インポート用の新規雛形 CSV** をまとめて作りたいとき

### 何を出力するか

- 差分レポート（Excel）：行ごとに **OK / NG / 要確認 / データ欠損** を色分け判定
- 未提出者一覧
- 新規雛形 CSV（jinjer にそのままアップロード可能）

### 使ううえでの注意

- 勤務表は **Claude（AI）の OCR / 解析**で読み取ります。読み取り結果は**最終的に人の目で確認**してください（特に手書き・低画質のスキャン）。
- アップロードしたファイルや出力は**共有フォルダ上**に作られます（下記「データの置き場所」参照）。個人情報を含むため取り扱いに注意してください。
- **このツールは「気づきの補助」です。** 請求・給与へ反映する前の最終判断は必ず担当者が行ってください。

## ✨ 主な機能

| 機能 | 内容 |
|---|---|
| 勤怠突合 | jinjer CSV と勤務表ファイル（複数可）を突合、差分を OK / NG / 要確認 / データ欠損 で判定 |
| 多形式対応 | 勤務表は xlsx / xls / pdf / png / jpg / jpeg に対応（Claude Vision で OCR）|
| 未提出者検出 | jinjer に居るのに勤務表が無い人を一覧化 |
| 氏名の近似一致 🆕 | スキャンPDFのOCRが氏名を**1文字だけ誤読**しても（例: `矢野瑞穂`→`矢野瑞也`）、jinjer側に唯一の近似候補があれば自動で同一人物として突合し、jinjerの正しい氏名に寄せる。誤マッチ防止のため**4文字以上のフルネーム・編集距離1・候補が1人だけ**の場合のみ適用 |
| **シフト記号対応** 🆕 | `B = 12:30-21:00`、`● = 夜勤`、`明 = 休` のような **記号式シフト表を自動で時刻化**（凡例レビュー UI 付き）|
| **新規雛形 CSV 生成** 🆕 | jinjer 既存雛形にマッチしない記号は **インポート用 CSV を自動生成**。人間はそのまま jinjer にアップするだけ |
| **24:00跨ぎ統合** 🆕 | `4 (16:30-24:00) + a (24:00-翌09:00)` を `16:30-翌09:00` の 1 レコードに統合 |
| **KDXシフト表PDF対応** 🆕 | KDX（ユニアデックス作成）の勤務シフト表PDFを **AIを使わず構造化解析**（`services/kdx_shift_parser.py`）。セルの記号（A1〜A6/C1〜C6）は休憩時間帯コードで勤務時間の記載が無いため、固定勤務時間（日勤9:00〜17:30・夜勤16:30〜34:00）を補って雛形へ自動マッチ。`ー`=夜勤明け→「休み」、`／`=公休→所/法、`有`=有給→一般雛形。2026-07実PDFで11名×31日の完全一致を確認済み |
| **BBS勤務表xlsx対応** 🆕 | BBS（ブロードバンドセキュリティ）の勤務表xlsxを **AIを使わず構造化解析**（`services/bbs_shift_parser.py`）。1人＝3行（計画／リーダー／時間）で日は列位置だけが手がかりのため、AI読み取りだと**行頭が空欄の人だけ1日ズレる**（2026-09 加藤 英人さん＝9/1が空欄で3回中2回ズレた実測）。列位置で読むので空欄もそのまま「その日は休み」になる。凡例（`A=8:00～20:15` / `B=20:00～32:15` / `E=9:00～18:00` ほか）はシート最下段から読み、書かれていない月は既定値で補って画面に出す。**氏名が「(N)」で始まる行＝当社社員だけ**を取り込む（BBS側要員の混入防止）。計画が空の日のリーダー行メモは**休暇だけ**記号として拾い、勤務地メモ（「新宿」等）は警告に回す |
| **SAP重複除外＝取込済み費用シート台帳（経費）** 🆕 | SAPの月次経費CSVに混ざる**前々月分の再掲を取込前に除外**（`services/sap_import_ledger.py`）。**過去CSVの指定は 2026-08-06 に廃止**し、取り込んだ費用シートを台帳（`Y:\給与明細\_SAP取込済み費用シート台帳.csv`）に記録して翌月は台帳と突合する。判定は3段階＝**明細まで一致→除外／費用シートIDだけ一致→★要確認（金額訂正の再発行の可能性。自動除外も自動取込もしない）／台帳に無い→取込**。証跡はExcel「SAP除外(支給済み)」「SAP要確認」シート＋同名CSV。判定に使うのは**確定分のみ**で、取込後に画面の「台帳を確定」を押す。台帳への書き込みは許可ユーザーのみ（`Z:\API連携\docs\SAP台帳_書き込み許可ユーザー.csv`）。<br>旧方式（前月の生CSVと突合）は、どのファイルで取り込んだかを人が思い出す必要があり、2026-08-06 に別DLを指定して**285,642円が二重支給になりかけた**ため廃止。`services/sap_duplicate_filter.py` はその名残で**現在どこからも使っていない** |
| **経理モード** 🆕 | 支給月を入れるだけで jinjer の給与明細から **freee 取引インポート用の4CSV**（給与／住民税／健康保険／厚生年金・17列cp932）を生成（`services/keiri_engine.py`）。**検算**と**要確認リスト**、経理担当の最終CSVがある月は**差分突合**も画面に出る。給与の「その他」は経費一覧表マクロの明細から費用品目へ自動分解（`services/keiri_keihi_tenki.py`）。2026-07 実データで住民税・健保・厚年は完全一致、給与も金額差0 |

## 🧾 経理モード（freee 給与仕訳の生成）

毎月の給与仕訳を freee へ取り込む作業を自動化する。手作業だった VLOOKUP の部門補完・
取引分割・経費転記をシステム側で行うので、`#N/A` のような転記事故が起きない。

- **入力**: jinjer の給与明細 API（当月と前月の2か月ぶん。月別 JSON にキャッシュするので2回目以降は速い）
- **マッピング表**: `Z:\API連携\docs\経理モード_品目マッピングマスタ_draftC.csv` と
  `…_経費転記マッピング_draftD.csv` を**共有フォルダから読む**。表を直せば **exe の再ビルドなしで**
  次回実行から効く（画面の詳細設定でパスを一時的に差し替えることもできる）
- **経費転記の材料**: `Y:\給与明細\R8年\{M}月\経費利用履歴 RevN.xlsm` の「集計ログ」。
  無い月は分解せず、要確認リストに出して手で足してもらう
- **出力**: `outputs/keiri/{YYYYMM}/`（4CSV＋検算＋要確認＋差分。個人情報を含むので非コミット）
- **安全弁**: 分解した経費の合計が jinjer の「その他」と1円でも違う人は行を作らず要確認へ回す

ロジックの本体はこのリポジトリにあり、`Z:\API連携\scripts\keiri_run.py` は開発用の CLI ラッパ。
マッピング表の作成・レビュー資料の生成は `Z:\API連携` 側の開発ツールが担当する。

## 🩺 健康診断HPMモード（HPM取込用CSVの生成）

健診PDFから起こした整形済みExcel（スキーマ2.0）を読み、HPM取込用の302列CSVを作る。
**HPMへの読み込み・チェック・更新は従来どおり手作業**で、このモードはCSVを作るまで。

- **入力**: 健診機関から届いた **PDF をそのまま**、または `health-check-pdf-to-excel` スキルが
  出力した整形済み `.xlsx`（スキーマ2.0）。旧スキーマ（v1）はプレビューだけでき、
  CSV生成は「原票PDFからスキーマ2.0で再整形してください」で止まる
- **変換マスタ**: `Z:\NMHT総務関係\健康診断\健康診断HPM変換マスタ.xlsx` を**共有フォルダから読む**。
  健診機関コード・健診種別・302列ヘッダー・項目マッピングをこのファイルで持つので、
  項目や機関が増えても **exe の再ビルドなしで**反映できる。
  再作成は `python tools/build_health_hpm_master.py`
- **jinjer照合**: 氏名・性別・受診日時点の年齢がすべて一致したときだけ自動確定。
  同姓同名や不一致は画面で人が選ぶ（別人のIDを書かないため）
- **出力**: `Z:\NMHT総務関係\健康診断\{年度}\{年度}年度健康診断受診者結果\CSV格納\`
  （302列・CP932・BOMなし・CRLF。年度は受診日の会計年度で4月始まり）

### 守っているルール

- **血圧の平均値は作らない**。1回目（列50/51）と2回目（列52/53）を原票のまま別々に出す。
  1回分しかなければ2回目は空欄のまま（複製しない）。3回目以降は保持するがHPMへは出さず警告する
- `(-)` は陰性を表す**有効な値**として出力する。`（－）` などの表記ゆれは `(-)` に寄せるが、
  **空欄や括弧のない単独ハイフンを勝手に `(-)` にはしない**（未実施と区別できないため）
- 原票の判定（A〜G）はHPMのマスタコードと体系が違うので**転記しない**（判定列183〜197は空欄）
- 変換マスタの血圧が50〜53からずれていたら、読み込んだ時点でエラーにして1バイトも出力しない
- 書き出したCSVはバイトから読み直し、行数・列数・全セルの一致を確認してから完了にする

> ⚠️ **生成したCSVをExcelで開いて保存し直さないこと。** 受診番号の先頭ゼロ（`000132`）が落ち、
> 行が消えることがある（2026-08 に共有フォルダの修正版CSVで実際に発生し、6名→4名になった）。

### PDFを直接読ませる場合

PDFを選ぶと、各ページを画像にして Claude が読み取る（勤務表のAI読み取りと同じ扱い）。
1人あたり10〜20秒かかるので進捗が流れる。読み終わると**各人の欄に原票のページ画像**が出るので、
値と見比べてから「原票どおり」にチェックを入れる。

- ページ全体だけでなく**上下2分割の拡大も一緒に送る**。全体1枚だけだと細かい数字が潰れ、
  2026-08 の検証で %肺活量(103.4) と 1秒率(82.5) が入れ替わった。どちらも実在する値なので
  BMI検算のような整合チェックでは気付けない
- 読めない値は推測させない。血圧の測定回が判断できなければエラーで止め、
  整形済みExcel経由でのやり直しを促す
- CSVを作ると、根拠として**原票画像つきの整形済みExcel**（`<PDF名>_Excel変換_整形済.xlsx`）を
  CSVと同じフォルダに残す。これは後からチェッカーに読ませ直すこともできる
- 検証は**同友会の個人票様式**で行った（6名228項目が全一致、3回繰り返してもブレなし）。
  他の機関の様式は読めるとは限らないので、表示された値を必ず原票と見比べること
- 1回に読めるのは既定20ページまで（`HEALTH_HPM_PDF_MAX_PAGES`）、PDFは50MBまで

健診結果は要配慮個人情報なので、プレビュー中の一時ファイルは共有フォルダではなく
各PCのローカル（`%LOCALAPPDATA%\KintaiChecker\health_sessions`）に置き、既定8時間で自動削除する。

## 📑 派遣台帳モード（派遣元管理台帳の四半期作成〜jinjer添付）

四半期ごとの派遣元管理台帳（労働者派遣法37条）を、画面から4ステップで作る（2026-08-28 追加）。
コアは `services/daicho/`（`Z:\API連携\派遣元管理台帳` から移設。旧側はCLI互換ラッパのみ）。
データは `Z:\派遣元管理台帳\`（`DAICHO_DATA_ROOT`）にあり、リポジトリには置かない。

1. **①入力ファイルを確認** — input/ の鮮度チェック（TC/CPIはファイル名のDL時刻、
   人マスタキャッシュは fetched_at、FG新レポートは期内WO件数まで見る。読むだけ）
2. **②台帳を作成** — e-staffing＋Fieldglass＋直接契約＋jinjerから台帳xlsx・一覧CSV・警告CSVを
   生成（約30秒）。警告一覧は前回build比の **新規/継続/解消** 付きでトリアージ表示。
   直す手段は原則「元データを直して再build」
3. **③PDFを出力** — 台帳ブックから人別フォルダへ契約ごとのPDF（Excel COM・1期約5分）
4. **④jinjerに添付** — menu16 へPDFを添付。**デタッチ子プロセス**で走るのでハブの窓を
   閉じても止まらない。「今すぐ」と「今夜22:00」の2ボタン（1期≈165枚×約60秒/枚≈3時間。
   夜間に回すのが既定＝jinjerのレート制限はテナント単位のため）。実行できるのは
   `Z:\API連携\docs\派遣台帳_書き込み許可ユーザー.csv` に載っている人だけ（フェイルクローズ）。
   添付は非同期（最大35分遅れ）なので翌朝「反映を確認（verify）」を押す。再実行は常に安全

- Fieldglass の入力は四半期メール（10/15・1/15・4/15・7/15）で届く**新レポート2本**を
  input/ に保存するだけ（ユニアデックスXLSX＝台帳の元データ、エリクソンCSV＝直接契約3人の
  現行値上書き）。旧 WO CSV＋詳細JSON も `--fg-mode legacy` で温存
- 1・4・7・10月に直前四半期が未作成だと、カード上部に作成時期のバナーが出る
- 標報投入と添付ジョブは相互にロックを見て同時実行しない（429がテナント単位のため）
- 設計と検証記録は [docs/PLAN_派遣台帳モード.md](docs/PLAN_派遣台帳モード.md)

## 👥 他の人にも使ってもらう（共有運用・ローカル同期版）

> 2026-07-02 より **ローカル同期方式** に変更。利用者向けの詳しい案内（日英併記）は
> [docs/起動方法_ローカル同期版.md](docs/起動方法_ローカル同期版.md) を参照。

`起動.bat` をダブルクリックすると、
1. NAS 上のマスター（`dist\KintaiChecker`）が更新されていれば、利用者 PC の `%LOCALAPPDATA%\KintaiChecker` へ **robocopy で差分同期**（更新なしなら比較2ファイルのみで即スキップ）
2. **ローカルの EXE** を起動（→ 起動が速い・何人が同時に使ってもOK・NAS 直接実行のロック問題なし）
3. すでに起動中なら、ブラウザを開くだけ（二重起動しない）

利用者は Python のインストール不要。**起動.bat への「ショートカット」をデスクトップに置いて使う**（bat 本体のコピーは禁止。コピーすると更新が反映されなくなる）。

### 配布側（管理者）の運用ルール

| 場面 | やること |
|---|---|
| 機能を追加した／不具合を直した | **必ず exe を再ビルド**（`kintai-exe-builder` エージェント推奨。使用中swap事故防止）して NAS の `dist\KintaiChecker` を最新化。各利用者 PC へは**次回起動時に自動同期**されるので配り直し不要 |
| 新しい人に渡す | `起動.bat` へのショートカット作成手順を案内するだけ（docs/起動方法_ローカル同期版.md 参照） |
| `.env` を更新した | NAS 直下の `.env` を書き換えるだけで、**再ビルド不要**で次回起動時に各 PC へ自動配布される（起動.bat が `.env` も同期対象にしている） |

### よくある「動かない」と対処

| 症状 | 原因 | 対処 |
|---|---|---|
| 初回起動が数分かかる | 約200MBのローカルコピー作成中（初回のみ） | そのまま待つ。2回目以降は速い |
| ブラウザが開かない | サーバー起動前にタイムアウト | ブラウザで `http://localhost:5000` を手動で開く |
| 「[WARN] Could not update the local copy」と出る | ローカル同期失敗（権限・ディスク容量等） | そのまま NAS 版で起動する（遅いが使える）。続くなら管理者へ |
| 「KintaiChecker.exe が見つかりません」と出る | NAS のマスターが未ビルド | 管理者に依頼 |
| ダブルクリックしてもブラウザが開くだけ | すでに起動中（正常動作） | そのまま使ってOK。止めたい場合は先に開いた黒い画面を閉じる |

### データの置き場所（ローカル同期版）

| フォルダ | 用途 | 扱い |
|---|---|---|
| `%LOCALAPPDATA%\KintaiChecker\uploads/` | アップロードした jinjer CSV・勤務表（処理後に自動削除） | **各利用者の PC 内**。他の人と混ざらない |
| `%LOCALAPPDATA%\KintaiChecker\uploads\sessions/` | 凡例レビュー中の中間状態（pkl） | 同上。古いものは手動削除OK |
| `%LOCALAPPDATA%\KintaiChecker\outputs/` | 突合結果 Excel など | **各利用者の PC 内**。取り出しは画面の「ダウンロード」ボタン経由（従来どおり） |

> 利用者ごとに完全分離されたため、旧方式にあった「同名ファイルの後勝ち上書き」「共有 uploads にゴミが残る」問題は解消。

## 🔄 処理フロー

### A. 直接時刻が書かれた勤務表（既存）

```
[jinjer CSV]  +  [勤務表（時刻直書き）]
   ↓                  ↓
   └──┬───────────────┘
      ▼
   突合 → Excel 出力
```

### B. シフト記号で書かれた勤務表 🆕

```
[jinjer CSV] + [勤務表（記号式）]
   ↓               ↓
   ↓          Claude API でモード判定
   ↓          → "code" モード検出
   ↓               ↓
   ↓          凡例＋シフト表 抽出
   ↓               ↓
   ↓          【凡例レビューUI】← 人間が確認・修正
   ↓               ↓
   ↓          記号 → 時刻 解決（24:00跨ぎ統合含む）
   └──┬───────────┘
      ▼
   突合 → Excel 出力
   ＋ jinjer 雛形にない記号があれば「新規雛形 CSV」も同時生成
```

## 🆕 シフト記号対応の仕組み

### 1. 自動モード判定

Claude API が勤務表を見て、以下を自動判定します：

- `direct` モード：時刻が直接書かれている（例: 9:00-17:30）
- `code` モード：記号式（例: B, ●, A/B/明, 2/4/a）+ 同じファイルに凡例あり

### 2. 凡例レビュー UI

`code` モードと判定された場合、抽出された凡例が **編集可能なテーブル** で表示されます。

| 記号 | 種別 | 出勤 | 退勤 | 休憩(分) | 休? | jinjer 雛形 |
|---|---|---|---|---|---|---|
| B | B勤 | 12:30 | 21:00 | 60 | □ | 新規雛形候補 |
| ● | 夜勤 | 16:30 | 25:00 | 60 | □ | No 38 夜帯シフト |
| 明 | 明け休 | — | — | — | ☑ | — |
| 振 | 振休 | — | — | — | ☑ | — |

- セルをクリックで直接編集できます
- 「休？」にチェックを入れるとその記号は **休扱い**
- jinjer 既存雛形にマッチした記号は **緑タグ**、しないものは **黄色タグ**で表示
- 「✅ この凡例で実行」を押すと突合へ進みます

### 3. 24:00 跨ぎ統合

連続する 2 日のシフトが 24:00 で繋がっている場合、1 レコードに統合されます。

```
田村さん:
  4日: 4 = 16:30-24:00
  5日: a = 24:00-翌09:00
   ↓ 統合
  4日: 16:30-翌09:00（実態は 33:00）
```

これは jinjer 側の打刻記録（1 シフト = 1 レコード）と整合します。

### 4. 新規雛形 CSV 生成

jinjer の既存雛形（`Z:\jinjer移行\カレンダー\スケジュール雛形一覧_*.csv`）と照合し、
マッチしない記号があれば **インポート用 CSV** を自動生成します。

```csv
No,勤怠スケジュール名称,略称(3文字以内),勤怠スケジュール名ID,予定区分,休日ID,出勤時刻(0:00~47:59),退勤時刻(0:00~47:59),...
56,B勤,B,B,9998,1,12:30:00,21:00:00,...
```

このまま jinjer にアップロードできます。

### 5. API直接投入（既定ルート・2026-07追加）

グリッドCSV生成後、画面には **🚀 APIでjinjerへ直接投入** ブロックが表示されます。
jinjer画面の月次スケジュールCSVインポートは一部従業員にサイレントに反映されない
事象があるため（2026-07に11名で実測）、**API投入が標準ルート**です。
生成されたグリッドCSVは控え・監査用で、画面からのアップロードは行いません。

1. **① 差分プレビュー** — jinjerの現状を取得し「誰の何日をどう変えるか」を表示
   （書き込みなし）。承認用Excelも出力されます
2. **② この内容で投入** — 差分がある日だけ書き込み、反映を1行ずつ自動検証
3. 「要手動確認」に出る項目（休日に予定残存＝画面から手動削除、休暇登録日など）は
   レポートの指示に従って個別対応

コマンドラインからも同じ処理ができます（作成済みグリッドCSVの再投入）:

```bash
python schedule_import_run.py <グリッドCSV|フォルダ>... --month 2026-08            # dry-run
python schedule_import_run.py <グリッド...> --month 2026-08 --execute --expect 123  # 投入＋検証
```

詳細設計: `docs/PLAN_スケジュールAPI投入.md`
