# PLAN: 手順③に jinjer API 直接投入を組み込む

**作成日**: 2026-07-09
**背景セッション**: 汎用データ画面インポートがスケジュール列をサイレントに反映しない不具合（サポート問い合わせ中）を、`POST /v1/kintai-imports` で回避できることを実証済み（石橋9999999テスト → 矢野2023026の月次21日 → 一括154行中150行反映、すべて work-schedules API で検証）。

## 1. ゴール

手順③（アップロード用CSV生成）の後工程を、

```
現状:   CSV生成 → ダウンロード → 人がjinjer画面で汎用データインポート → 反映確認は目視
提案:   CSV生成 → [🚀 APIで直接投入] → ステータス自動追跡 → 反映を1行ずつAPI検証 → OK/NGレポート
```

に置き換える（従来のCSVダウンロードも残す＝フォールバック兼監査用）。

**効果**:
- 画面インポート不具合の恒久回避（スケジュール列が確実に入る）
- 手動アップロード作業の廃止＋「入ったかどうか」を目視ではなく機械検証
- NG行が理由付きで残る（休暇日スキップ=対応不要 / その他=要手動）

## 2. 実証済みの技術要素（Z:\API連携\scripts に動作コードあり）

| 要素 | 実証内容 | 移植元 |
|---|---|---|
| `POST /v1/kintai-imports` | JSON `{type:{id:"5"}, input_file:{name, encoded_string(Base64のShift_JIS CSV)}}`。5000行以内。同時予約1件 | `fix_schedule_via_api.py` |
| ステータス追跡 | `GET /v1/kintai-imports` を20秒間隔ポーリング。status 0=予約/1=成功/2=失敗（行単位エラー詳細は無し→検証で補完） | 同上 |
| 反映検証 | `GET /v1/employees/work-schedules`（予定・休憩予定・24時超対応）＋ `GET /v1/employees/attendances`（打刻） | `month_schedule_via_api.py` |
| 休暇日ガード | 休暇登録日はスケジュールがサイレットに上書きされない（守屋6/23半休で実測）→ 休日休暇名1／種別／AM・PM有休で事前除外。`GET /v1/employees/requested-day-offs` で半休時間帯も取得可 | `fix_schedule_via_api.py` |
| スケジュール書き込みの副作用 | 日単位の丸ごと置き換え。**休憩予定時刻1〜5／復帰予定時刻1〜5 を必ずセットで送る**（送らないと休憩予定が消える。矢野さんで実測→修正済み） | 同上 |

※ quick_export は既に打刻・スケジュール・休憩予定を含む完全な行を出力するため、CSV生成側の変更はほぼ不要。

## 3. 実装項目

### P1: services 移植（0.5〜1日）
- `services/jinjer_api_client.py` に追加:
  - `post_kintai_import(csv_bytes, file_name, executor_id) -> import_id相当`
  - `list_kintai_imports(page)` / ファイル名でのステータス検索
  - `get_work_schedules(employee_id, month)`（休憩予定込み）
  - `get_attendance_times(employee_id, month)`（attended_at/left_at、24時超補正、重複除去）
- `services/kintai_import_runner.py` 新規:
  1. 生成済みアップロード用CSVを読み込み
  2. ガード: 休暇日行を除外（除外一覧を「要手動」として返す）。5000行超は分割
  3. POST → ポーリング（最大15分）→ status確定
  4. 検証: CSVの意図値（出勤予定/退勤予定/休憩予定ペア/出勤1/退勤1）と現物を突合
  5. 結果オブジェクト: 反映OK/NG行リスト（NG理由分類: 休暇日=対応不要 / 値不一致=要手動 / 検証不能）
- CLI エントリ（Web UIより先に動かす）: `python api_import_run.py <アップロード用CSV> [--execute]`

### P2: Web UI 統合（0.5〜1日）
- `app.py`:
  - `POST /kintai_import_api` … 投入ジョブ開始（スレッド実行、ジョブIDを返す。多重投入ロック＝同時予約1件制限に対応）
  - `GET /kintai_import_status/<job_id>` … 進捗（予約/処理中/成功/失敗/検証中/完了）＋最終レポートJSON
- `templates/index.html` 手順③セクション:
  - 本実行成功後に「🚀 APIでjinjerへ直接投入」ボタン（件数サマリ＋確認ダイアログ→開始）
  - 進捗表示（ポーリング）→ 反映OK/NG テーブル（NG理由付き、休暇日はグレー表示=対応不要）
  - 検証レポートxlsxのダウンロードリンク
- `config.py`: `JINJER_IMPORT_EXECUTOR_ID`（完了通知メールの宛先社員番号。未指定だとAPIキー紐付きの2018013山川さん宛になるため、谷津さんのIDを既定に）

### P3: テスト・ビルド・試運転（0.5日）
- pytest: 休暇日ガード／時刻正規化（秒付き・24時超・timedelta）／検証比較ロジック
- **カナリア試運転**: 石橋9999999で「打刻列を含む」1行投入→打刻もAPIルートで反映されることを確認（スケジュールは実証済み、打刻は画面ルートで実証済みだが、APIルート×打刻の組合せだけ未実測のため）
- exe再ビルド（build_exe_safe.py、dist_new→全員クローズ→swap手順）＋起動.bat同期確認

**合計目安: 1.5〜2.5日**（実証済みコードの移植が主体のため）

## 4. 安全設計（既存思想の踏襲）

- 「承認行のみCSVに乗る」ルールは quick_export がそのまま担保（変更なし）
- 保留行の除外・打刻削除日の要手動警告も既存のまま
- API投入は 確認ダイアログ → 投入 → 機械検証 の三段構え。dry-run（ガード・件数・除外一覧の表示のみ）を既定
- 投入履歴は jinjer 側にも残る（GET /v1/kintai-imports）＝監査可能
- 画面インポートが修理されても本機能はそのまま有効（むしろ標準ルート化を推奨）

## 5. 決定事項（2026-07-09 谷津さん確定）

1. **API投入を手順③の既定ルートにする**（CSVダウンロードは残す）。
   追加要件: **手動対応が必要な行（休暇日スキップ・検証NG・行スキップ等）を、インポート後にExcelブックで出力**する。
   列: 従業員番号 / 氏名 / 日付 / 区分 / 備考（理由）。
2. **executor = 9999999（管理部メール宛）案 → P3カナリアで権限不足が判明（2026-07-09）**。
   実測: executor に勤怠管理者ロールが無い社員番号（9999999・2026007 とも）を指定すると、
   **POSTは200で受理されるのに予約がキューに現れないままサイレント破棄**される。
   未指定（マスタ扱い→2018013山川さんへ自動解決）なら成功する。
   **当面の運用: executor未指定（既定値""）＋投入結果は画面とExcelレポートで確認**。
   管理部メール宛にしたい場合の手順（谷津さんのjinjer画面操作が必要）:
   ① jinjer ロール設定で 9999999 に勤怠管理者権限ロールを付与
   ② `.env` に `JINJER_IMPORT_EXECUTOR_ID=9999999` を追記
   ③ カナリア（1行投入）で通知メールが管理部に届くことを確認
3. 着手タイミング: **P1（services＋CLI）は即時着手**（バグ修正セッションと非競合ファイル）。P2/P3（UI・exe再ビルド）は quick_export timedelta 修正のマージ後にまとめて実施。
