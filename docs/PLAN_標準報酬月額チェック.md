# 標準報酬月額チェック（定時決定・保険料突合）

4〜6月支給の報酬から9月適用予定の標準報酬月額を計算し、jinjer の登録値・控除実績と
突合する CLI ツール。**jinjer へは読みに行くだけで一切書き込まない。**

```
python shaho_check_run.py --year 2026 --check-month 2026-07
```

- 実装: `services/shaho_master.py`（マスタ）・`shaho_engine.py`（算定）・
  `shaho_check.py`（判定）・`shaho_report.py`（出力）／CLI `shaho_check_run.py`
- テスト: `tests/test_shaho.py`
- 出力: `outputs/shaho/{年}/標準報酬チェック_*.xlsx`＋同名 `.json`（個人情報・ローカル限定）
- 終了コード: 0=要確認ゼロ / 2=要確認あり / 1=エラー

## マスタ（どちらも壊れていたら1円も計算しない）

| マスタ | 場所 | 中身 |
|---|---|---|
| 等級表Excel | `Z:\API連携\標準月額資料\令和8年度_…比較.xlsx` | 健保50等級・厚年32等級・料率。見出し名でパースし、連番・半開区間の連続性・保険料額列=標報×率・年度を総当たり検証 |
| 報酬分類マスタ | `Z:\API連携\docs\標報チェック_報酬分類マスタ.csv` | 支給項目ごとの 対象/現物/対象外/未設定 ＋固定的賃金フラグ＋**適用期間**。再生成は `tools/build_shaho_class_master.py` |

翌年度は等級表を差し替えて `--year` を変えるだけ（年度が合わないと停止する）。

## 肝: 検算ゲート

**報酬計（分類=対象の合計）＝ jinjer の雇用保険対象額(other5)** が全員で成立することを
毎回確かめる。1円でもズレた人は算定を信用せず「情報不足」へ落とす。分類ミス・jinjer の
項目変更・新項目の出現がすべてここで捕まる（2026-04〜06 の実データ全713人月で一致）。

このゲートが発見した月替わりの罠（分類マスタの適用期間で吸収済み）:
- 2026-04 は旧体系の最終月（体系名「140-180時間制暫定」「時給制暫定」）。
  `a6 過不足調整/法定休日勤務分` は4月だけ実支給。`a8` は暫定支給額の再掲（グロス外）
- 時給制の「みなし給」(a2) は 2026-07 以前が再掲・2026-08 から実額（同じラベルで意味が変わる）
- `a54 支給過不足調整` は実支給（対象）
- `a53 現物支給` は 〜2026-04=労務の対象（現物）／2026-05〜=Amazonギフトカード（対象外）。
  分類「現物」は報酬に数えるが現金グロスの外なので検算からは除く

## 支払基礎日数は「ラベル」で引く（項目IDは月で意味が変わる）

**2026-04（旧体系）と 2026-05以降で勤怠項目のID配置が全く違う。**

| ID | 2026-04 | 2026-05以降 |
|---|---|---|
| kintai6 | 出勤日数 | 内前月実績超過勤怠時間60時間以上 |
| kintai8 | 前月有給消化日数 | 前月の法定休日労働時間 |
| kintai10 | （無し） | 出勤日数 |
| kintai13 | （無し） | 前月有休消化日数 |

IDで引くと時給制の4月が全員「出勤日数0日」になり、丸ごと算定から外れる（2026-08-17 に発覚）。
支給項目と同じくラベルで引く。「有給」「有休」の表記ゆれも吸収する。

### ⚠ 2026-05 の時給制はラベルすら信用できない（スロット直読みで補正）

**値は旧配置のまま、ラベルだけ新体系に差し替わっている**移行途中の状態だった:

| スロット | 5月のラベル | 実際の中身 | 根拠 |
|---|---|---|---|
| kintai6 | 内前月実績超過勤怠時間60時間以上 | **出勤日数** | 46名・中央値20.0日（4月の出勤日数と同じ分布） |
| kintai8 | 前月の法定休日労働時間 | 前月有給消化日数 | kintai13と値が完全一致 |
| kintai9 | （名前なし） | 有給休暇残 | kintai14と値が完全一致 |
| kintai10 | 出勤日数 | **空** | 移行されなかった |
| kintai11 | 欠勤日数 | 総法定外残業時間 | 最大60。日数ではない |

有休まわりは新スロットへコピーされたのに**出勤日数だけ取り残された**。
`SLOT_OVERRIDES` で 2026-05 の時給制だけスロットを直接指定して読む（過去月なので値はもう動かない）。

**効果**: 5月の採用が0名→38名に回復し、8月登録との一致が110名→118名に増えた。

### 支給項目のラベルも月でずれる（報酬計算には影響しない）

時給制の allowance2/3/4 は 2026-06/07 だけラベルが1つずれている
（05・08: a2=みなし給／a3=前月超過勤務、06・07: a2=前月超過勤務／a3=前月深夜残業分）。
分類マスタは a3〜a6 を期間によらず「対象外」にしており、a2 だけ体系別名＋期間で
判定しているため**報酬計算には影響しない**（検算ゲートが全713人月で通ることが裏付け）。

## 実績: jinjerの手入力ミスを1件検出した（2026-08-17）

**2026-08 に登録が動いた33名のうち32名は当方の計算と完全一致**。残る1名
（遠田恭実2024027）の不一致を追った結果、**jinjerへの手入力ミス**と確定した。
**当方の 280,000 が正しく、登録されていた 300,000 が誤り**だった。

| 支給月 | 通勤費 | 中身 |
|---|---|---|
| 2026-04 | 15,700 | 旧額（本来26,950） |
| 2026-05 | 15,700 | 旧額 |
| 2026-06 | 49,450 | 当月分26,950 ＋ 4・5月の差額22,500 |
| 2026-07・08 | 26,950 | 新額で安定 |

通勤手当が4月から上がり、差額が6月にまとめて出ていた。登録の300,000は
「6〜8月平均で遡及分を除かずに計算した値」(292,644) とだけ一致し、他のどの見方でも
280,000（定時決定4〜6月＝283,761／遡及分を除く6〜8月＝285,144）。
関東IT健保から変更通知が来ていないことも決め手になった。

**調査の型**: 不一致は月次推移を並べて構造を掴む。金額が「当月分＋遡及分」に
分解できるかを確かめると原因が割れる。

### 既知の限界: 通勤手当の変動は随時改定候補に挙がらない

`REVISION_IGNORE_KEYS` で通勤費を固定的賃金の変動検知から外している（実費精算の人が
毎月動くため。入れると134名の過検知になる）。定期代の改定は候補に出ないので、
「3か月続けて同額なら改定とみなす」等にすれば拾える。優先度は低い。

## 判定（要確認系は絶対に自動OKへ昇格しない）

標報判定と控除判定の2系統。総合は優先順位の強い方:
`情報不足 > 免除の確認 > 2か月徴収の確認 > 社保調整あり > 随時改定の候補 > 差異 > 仮OK > OK > 対象外`

- **控除突合**: C月明細の本人控除4種（健保・介護・厚年・子育て支援金）は
  **（C−1）月分**（jinjer設定「翌月徴収」）。基礎標報は（C−1）月スナップショットの登録値
  × 本人負担率、丸めは50銭以下切捨て・超切上げ（`SHAHO_ROUNDING` で変更可・±1円は仮OK）
- **随時改定候補**: 4〜6月に固定的賃金（通勤費は除く＝実費で毎月動くため）が変動し、
  変動月から3か月平均が登録と2等級以上差、または窓が閉じない人
- **免除**: `is_shaho_menjo_prev`（前月分の会社負担あり∧当月控除ゼロ）。控除0が正でも要確認
- 6/1以降入社・8月末まで退職＝定時決定の対象外。休職で採用月ゼロ＝情報不足（保険者算定の可能性）

## 2026-07 突合の実績（初回実行）

対象240名: OK 49・仮OK 30・差異126・随時改定候補3・免除5・2か月徴収1・情報不足10・対象外16。
**控除突合で説明できない差は0名**（167名完全一致・48名±1円）。
「差異」は現登録（2025年9月決定ベース）と今年の計算値の差＝**9月に改定されるべき人リスト**。

## 運用（毎月やること）

1. 経理モードを回せば statements キャッシュが月次で増える（それをそのまま使う）
2. 9月・10月のキャッシュが増えたら `--check-month` を進めて再実行 →
   「差異」が消えていれば定時決定が正しく反映された、が答え合わせになる

### キャッシュの再取得について（2026-08-17 実測で確認）

**登録標準報酬月額はその支給月の値で、給与が確定した月は凍結される。**
2026-06 を 7/24 取得分と 8/17 再取得分で比較したところ、実社員232名は完全に一致した。
動いたのは `is_payroll_closed=False`（給与未確定）のテスト社員9999999の1名だけ。

したがって過去月を取り直しても期中改定の検知は壊れない。ただし:

- **給与が未確定の月のスナップショットは信用しない**（値がまだ動く）
- 取り直す実益は無いので、通常はキャッシュをそのまま使えばよい
  （jinjer のレート制限は他システムとテナント単位で共有している）
