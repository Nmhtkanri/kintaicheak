# 社労士モード（前田事務所へ渡す給与CSV）

jinjer の給与明細から、社労士（前田事務所さん）へ毎月渡している CSV を作るモード。
**jinjer へは読みに行くだけで、一切書き込まない。**

- 実装: `services/sharoushi_export.py`（純ロジック）／`app.py` の `/sharoushi_run`・`/sharoushi_download`
- 画面: モードタブ「社労士CSV」
- テスト: `tests/test_sharoushi_export.py`、`tests/test_app_sharoushi_ui.py`
- マスタ作成: `python tools/build_sharoushi_masters.py`
- 出力: `outputs/sharoushi/{YYYYMM}/前田事務所{作成日}.csv` と `備考{作成日}.csv`（cp932・CRLF・非コミット）
  - 旧60列で出したときは `前田事務所{作成日}_旧60列.csv`（同じ日に両方作っても上書きしないため）

## なぜ作ったか

2026-07 支給分までは手作業で作って社労士へ渡していた。見本ファイル
（`前田事務所20260813.csv` ＝ 2026-07 支給分）を jinjer の実データと突き合わせたところ、
**60 列すべてが給与明細 API だけから機械的に再現できる**ことが分かったので自動化した。

初回の本番運用は **2026-08 支給分**。

## レイアウト V1 / V2（2026-08-28）

見本を写した 60 列には、jinjer 側に対応項目が無いか一度も金額が出たことのない列が
**13 列**あり、構造的に常に空だった。一方で毎月金額が動いている社保調整・社宅家賃・
貸付金返済には専用列が無く、合計欄の中に溶けていた。そこで列を入れ替えた。

| | 列数 | 位置づけ |
|---|---|---|
| **LAYOUT_V2** | **49列** | 既定。社労士へ渡す正本 |
| LAYOUT_V1 | 60列 | 社労士の受け入れ確認が済むまでの控え。画面の「旧60列のまま出す」で選ぶ |

V2 での変更点:

1. **「欠勤控除」列を「社保調整」に転用**（値は `deduction4`）。
   欠勤控除(`deduction1`)は 2026-04〜08 の5か月とも全員ゼロで、列として機能していなかった
2. **常に空だった13列を削除** — 超過時間(5)・超過時間分(17)・深夜残業分(18)・休日出勤分(19)・
   休日深夜分(20)・控除精算(21)・超過精算分(22)・超過調整分(23)・職能手当(26)・営業手当(28)・
   現場管理費(30)・家賃手当(33)・欠勤控除額(36)（カッコ内は旧60列での番号）
3. **課税対象額を埋める**（`salary_other_items:other7`）。旧60列では見本に合わせて常に空だったが、
   jinjer には毎月 230 名・7,900 万円台の値がある
4. **社宅家賃・貸付金返済に専用列を新設**（`deduction2` / `deduction3`）
5. **重複していた見出しを jinjer の項目名に合わせた** — 旧60列は「過不足調整」が2つ、
   「超過時間」も2つあり、どちらが何なのか見出しから読めなかった。
   X列 `差額調整`（allowance24）／AB列 `支給過不足調整`（allowance54）に改名し、
   「超過時間」の重複は列削除で解消した。**V2 の見出しはすべて一意**
   （`LayoutTests.test_v2_headings_are_unique` で担保）

**V1 の見出しは変えていない。** V1 は「昔どおりの形」を再現するのが役目で、見本 231 行との
突合とバイト一致の土台になっているため。レイアウトごとの見出し上書きは `Layout(labels=...)`。

課税通勤費と年調過不足額は実績ゼロだが **残した**。前者は通勤費が月額上限 3 万円を超えたとき、
後者は年末調整（12月支給）で発生しうるため。

**⚠ 社労士の受け入れ確認が済んだら、V1 レイアウト・`silent_hidden`・`_旧60列` サフィックス・
旧マッピングCSV をまとめて撤去すること。** 残り続けるフォールバックは腐る。

## 入力

給与明細 API（`/v1/employees/salary-statements`）**1本だけ**。
`statements[].basic_info` に氏名（last_name / first_name）と給与体系（`salary_system.name`）が
入っているので、従業員マスタの別取得は要らない。
キャッシュは経理モードと共用する（`outputs/keiri/raw/salary_statements_{ym}.json`）。

外部マスタ（どれも共有フォルダ。直せば exe の再ビルドなしで次回実行から効く）:

| ファイル | 既定パス | 役割 |
|---|---|---|
| 列マッピング | `Z:\API連携\docs\社労士モード_列マッピング_v2.csv` | どの列にどの jinjer 項目を入れるか |
| 追加支給台帳 | `Z:\API連携\docs\社労士モード_追加支給台帳.csv` | 給与計算後に発生した支給を足す |
| 備考台帳 | `Z:\API連携\docs\社労士モード_備考台帳.csv` | イレギュラー5項目の発生理由 |

列マッピングが無いときはコード内の既定表（`DEFAULT_COLUMN_MAPPING`）で動く。

## 列は「番号」ではなく「列id」で指す

2026-08-28 に13列を削って番号が総ずれしたので、マッピングのキーを **列番号 → 列id**
（`kihonkyu`・`shaho_chosei` のようなスラッグ）に変えた。番号のままだと、古い表が残っていた
ときに**値が黙って別の列へ入る**（社労士に誤った金額が渡る）ため。

そのため **旧スキーマ（`列番号` 見出し）のファイルは読まずにエラーで止める**。
出たら `python tools/build_sharoushi_masters.py` で作り直す。
ほかに、未知の列id・列名と列idの食い違い・予約列（社員番号/氏名/給与体系）・計算列の指定も
エラーにする。列名は注記だが、列id と食い違っていたら人が誤解しているので止める。

列マッピングCSVの列: `列id, 列名, 給与体系, 社員番号条件, source_key, 体系別名条件, 備考`

- 給与体系が空 = 全体系共通 / 体系別名条件が空 = 条件なし / 社員番号条件が空 = 全員
- 同じ（列id, 給与体系）の行が複数あるときは**合計**する
- **社員番号条件つきの行は、同じ source_key の条件なし行より優先する**（その社員に限り
  条件なし行を無効にする）。取られた側の列は空欄ではなく 0 にして、列の中身を不揃いにしない

## 列の対応

**給与体系ごとに中身が変わる**（月給制1／月給制2／月給制3／時給制1／管理監督者）。

計算で埋める列（マッピングでは指定できない。カッコ内は V2 での列番号）:

| 列 | 式 |
|---|---|
| 28 総支給額 | `雇用保険対象額(other5)` そのまま |
| 41 社会保険料計 | 雇用保険＋健保＋介護＋厚年＋子ども子育て支援金＋**社保調整(deduction4)** |
| 42 控除合計 | 社会保険料計＋所得税＋住民税＋年調過不足＋**欠勤控除＋社宅家賃＋貸付金返済** |
| 43 差引支給額 | `差引支給額(payment1)` そのまま |
| 44 口座1振込額 | `口座1振込額(payment2) − 立替金(a51) − 立替金（顧客請求分）(a50) − その他(a52)` |

29 課税対象額 は計算列ではなくマッピング列（`salary_other_items:other7`）。

**⚠ 社保調整・社宅家賃・貸付金返済は V2 で専用列を持つが、上の式は変えていない。**
合計は列ではなく source_key を直接足しているので、列を作ったことで二重計上にはならない。
「合計に足し忘れでは？」と `KOJO_GOKEI_KEYS` を触ると
`test_kojo_gokei_is_unchanged_when_columns_are_added` が落ちる。

### 立替金と「その他」の扱い（いちばん間違えやすいところ）

**立替金2種と「その他」は報酬ではないので、総支給額と口座1振込額の両方から外す。
差引支給額からは引かない。**

- 総支給額が雇用保険対象額そのものでよいのは、jinjer の雇用保険対象額が元々
  立替金2種・その他を含まないため。それだけで「報酬でないものを除いた支給計」になる
- 差引支給額(payment1) にはこの3つが乗っているので、引いた額が実際の振込額になる
- 検算: `差引支給額 − 立替金 − 立替金（顧客請求分） − その他 ＝ 口座1振込額`（全員で成立）

「その他」(allowance52) は経費統合一覧表からの精算分で、消耗品費・社員育成費などに
分かれる経費。報酬ではないので 2026-08-14 に総支給額から外した（それまでは足していた）。

V2 で専用列を持たない控除は **欠勤控除(deduction1) だけ**になった。金額が出たら
「この形式に列が無い控除項目に金額があります」の警告に出る（下記）。

## ⚠ 貸付金返済が「社宅家賃」の枠(deduction2)に入る月がある

2023004 の役員貸付金返済 341,659 円は、jinjer 側の入力先が月によって揺れる。

| 支給月 | 入っていた項目 |
|---|---|
| 2026-05 | `deduction2`（**社宅家賃**の枠） |
| 2026-06 / 07 / 08 | `deduction3`（貸付金返済） |

合計欄の中にだけ乗っていた頃は無害だったが、**専用列を作ると「社宅家賃 341,659 円」という
嘘のCSVが社労士へ渡る**。そこで列マッピングに社員番号条件つきの行を1つ置いて、
この人の `deduction2` は貸付金返済列へ寄せている。

経理モードの `keiri_engine.YAKUIN_LOAN`（同じ揺れを別ロジックで吸収している）と対になって
いるので、**jinjer 側で項目を整理するときは両方を直すこと。**

さらに、社宅家賃・貸付金返済・社保調整・欠勤控除は**発生者を毎回内訳に出す**ようにした。
月に2〜4行しか出ないので、名前と項目の組み合わせが先月と変わっていれば目で分かる。

## 備考CSV（イレギュラー発生分の理由）

本体CSVと一緒に `備考{作成日}.csv` を出す。社労士は金額だけ見ても理由が分からないため。
列: 社員番号／氏名／給与体系／項目／金額／理由

対象は経費チェックモードの「イレギュラー経費」から手入力する5項目
（`services/keihi_payroll_import.py` の `MANUAL_ITEM_KEYS` と同じ）:

| 項目 | jinjer |
|---|---|
| 定常外業務対応手当 | allowance19 |
| その他手当 | allowance20 ＋ allowance21 |
| 現物支給 | allowance53 |
| 支給過不足調整 | allowance54 |
| 社保調整 | deduction4（控除項目） |

社保調整は V2 では本体CSVにも列がある。**本体＝金額、備考＝理由**の役割分担で、
どちらも金額の出どころは jinjer なので食い違わない。

**金額は jinjer が正、理由だけを台帳に持たせる**（二重管理にしない）。その月に金額が
発生した人だけが行になる。理由は画面の「イレギュラー発生分の理由」から入れて保存すると
台帳へ書かれ、そのまま作り直しが走る。理由を空にすると台帳から消える。

理由が未入力の行は画面に件数が出る。未入力でも備考CSVは出る（理由欄が空になるだけ）ので、
渡す前に埋めるかどうかは人が決められる。

2026-08 実績は10件（定常外業務対応手当2・その他手当2・現物支給2・支給過不足調整2・社保調整2）。

## 3つの検知（要確認に出る）

| 検知 | 何を見るか | なぜ要るか |
|---|---|---|
| **未知項目** | 支給・控除項目に金額があるのに出力にも計算にも乗っていない | jinjer 側の項目移設に気づく。**既定ではエラーで止める**（「このまま出力する」で続行可） |
| **列が無いのに金額** | その形式に列が無い控除項目に金額がある | V2 では欠勤控除が該当。列を失ったので、発生しても誰も気づけなくなるのを防ぐ。警告のみ |
| **全員ゼロの列** | 課税対象額・総支給額が全員ゼロ | `salary_other_items` は未知項目検知の**対象外**なので、jinjer が other7 を移設しても掛からない。7,900万円の列が丸ごとゼロで渡るのを防ぐ唯一の網 |

差額調整の再掲（allowance3〜6）と前月基礎時給（allowance7）は、意図して出さない項目として
`IGNORED_KEYS` に理由つきで登録してあるので未知項目検知に引っかからない。

## 月をまたぐと変わるもの（要注意）

| 項目 | 〜2026-07 支給分 | 2026-08 支給分〜 | 対処 |
|---|---|---|---|
| 調整手当 | `allowance15` | `allowance12` | マッピングに**両方**入れて合計（片方は必ずゼロ） |
| 時給制の allowance2 | 前月超過勤務（出さない） | みなし給（みなし給の列へ） | **体系別名で判定**。月で切らない |
| その他手当 | `allowance21` | `allowance20` | **両方**をその他手当の列に入れて合計 |
| 貸付金返済 | 月によって `deduction2` / `deduction3` | 同左 | 社員番号条件で貸付金返済列へ寄せる |

`allowance2` を ID だけで判定すると月給制と時給制で意味が違うため事故になる。
体系別名が「当月みなし時間外手当／当月みなし深夜手当／みなし手当／みなし給」のときだけ
みなし給の列に入れる。それ以外で「前月〜」でもない名前になったら未知項目として止める。

## 検知網が本番で効いた実例（2026-08 初回実行）

未知項目が4件出た。いずれも **その月から使われ始めた項目**で、見本ファイル（2026-07）が
全ゼロだったため列の対応が分からなかったもの:

- `allowance19 定常外業務対応手当` 2名 75,000円 → 定常外業務対応手当の列へ
- `allowance20 その他手当` 2名 104,220円 → その他手当の列へ

「その他手当」は jinjer に allowance20 と 21 の2つあり、経費の追加投入がどちらに着地するかは
jinjer 側のテンプレート設定が決める。実測で 2026-07 は 21、2026-08 は 20 だったので、
**両方を同じ列に入れて合計**する形にした（同じ月に両方が入ることはない）。

## 検証

2026-07 支給分のキャッシュで、見本ファイル **231 行 × 60 列が V1 レイアウトで一致**する
（`tests/test_sharoushi_export.py` の `RegressionTests`）。差分は決めた変更によるものだけ:

- 2017012 の職能手当 10,000 → 調整手当へ移動
- 7777777・9999999 の 2 行を出力しない
- 「その他」がある 13 名の総支給額・口座1振込額（見本は総支給額に足して口座1から
  引いていなかった。2026-08-14 に報酬から外す方へ変更）

**列ID化のリファクタでは、2026-05 と 2026-08 の V1 出力が改修前とバイト単位で一致する**ことを
確認している（`cmp` で突合）。`RegressionTests` は空欄を 0.0 に丸めて比べるので、
**空欄と 0 の取り違えはバイト比較でしか捕まえられない**。列まわりを触ったら必ずやること。

V1 と V2 は共有 45 列が全セル一致する（`LayoutCorrespondenceTests` と実データ 231 行で確認）。
合計欄も一致する＝専用列を作っても二重計上していない。

2026-08 の V2 実績: 課税対象額 230名 78,964,194 ／ 社保調整 2名（2025018 +3,060・2026005 −3,862）／
社宅家賃 1名 88,000 ／ 貸付金返済 1名 341,659。

## 運用

1. 画面で「社労士CSV」タブ → 支給月を入れる
2. **CSVの形式**を選ぶ（通常はそのまま新49列。旧60列で渡したいときだけチェック）
3. 実行し、要確認（未知項目・列が無いのに金額・全員ゼロ・想定外の給与体系・複数明細・
   理由未入力）が出ていないか見る
4. 内訳の「社宅家賃・貸付金返済・社保調整の発生者」が先月と同じ顔ぶれか確かめる
5. 「イレギュラー発生分の理由」を埋めて保存（保存すると自動で作り直される）
6. プレビューで先頭 10 人ぶんを確認
7. 本体CSVと備考CSVをダウンロードして社労士へ渡す

給与計算後に追加で支払った分があるときは、先に追加支給台帳へ 1 行足してから実行する。

## V1 → V2 の移行（2026-08-28）

列マッピングのパスを `社労士モード_列マッピング.csv` → `社労士モード_列マッピング_v2.csv` に
**分けた**。同じパスを上書きすると、新マスタを置いてから exe を差し替えるまでの間、
配布済みの旧 exe が停止する（旧 exe は `列番号` 見出しが無い行を全部捨て、マッピング0行 →
全項目が未知項目 → エラー）。パスを分ければこの窓がゼロになる。

1. `python tools/build_sharoushi_masters.py` で `_v2.csv` を作る（66行）
2. `--show` で「66行（読み元: ..._v2.csv）」を確認
3. exe を差し替える
4. 差し替え後、旧 `社労士モード_列マッピング.csv` を `_旧60列_使用終了20260828.csv` へリネームする
   （**消さない**。V1 で再現する必要が出たときの記録）
5. 追加支給台帳・備考台帳はスキーマが変わっていないので触らない
