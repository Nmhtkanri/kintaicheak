# 標報投入 — 社労士の保険料一覧表PDF → jinjer報酬月額

社労士（前田事務所）から毎月届く「保険料一覧表」PDFを読み、標準報酬月額を jinjer 人事労務の
報酬月額へ投入する。オペレーションハブの**社労士モード**に置いたカード。

**このモードだけが jinjer へ書き込む。** 階層は「書く（マスタ級）」で、本来は共有exeに入れない
決まりだが、2026-08-17 に谷津さんの判断で例外とした（全体マップ §2 に記録）。

## なぜ作ったか

2026-08-17 に手入力ミスが実際に見つかった。遠田恭実（2024027）の標準報酬月額が jinjer に
300,000 で登録されていたが、正しくは 280,000 だった（標準報酬モードが検出）。
PDFから機械的に投入すれば、この種の転記ミスは起きない。

## トリプルチェック

| # | 誰が | 何を見るか |
|---|---|---|
| A | 社労士 | PDFの標準報酬月額。**法的な正はここ** |
| B | jinjer | いま登録されている値。差分だけを書く |
| C | オペレーションハブ | 給与実績から**独立に計算**した値。A と食い違ったら投入から外す |

そのうえで **人（谷津さん）が画面で確認して実行**する。

### 判定ステータス

| ステータス | 条件 | 既定 | 承知投入 |
|---|---|---|---|
| `NO_CHANGE` 書込不要 | A = B（対象月時点で有効な値と同じ） | 選べない | — |
| `AUTO_OK` 投入できる | A ≠ B、A = C、PDF検算OK | ✔ チェック済 | — |
| `NO_CALC` 投入できる | A ≠ B、C が出せない（取得時決定・料率変更・キャッシュ欠落） | ☐ | 不要 |
| `CALC_MISMATCH` 要確認 | A ≠ B、A ≠ C | 除外 | 可 |
| `PDF_INCONSISTENT` 要確認 | 行の読み取り異常・料率検算NG | 除外 | **不可** |
| `NOT_IN_JINJER` 要確認 | 社員番号が jinjer に無い | 除外 | 不可 |
| `RETIRED` 要確認 | jinjer上は退職 | 除外 | 可 |
| `EXCLUDED` 対象外 | 20YY 始まりでない | 除外 | 不可 |

## 入力は2種類ある

| 通知 | ファイル | 中身 | モジュール |
|---|---|---|---|
| 社労士（前田事務所）の保険料一覧表 | PDF | その月に保険料が変わった人。**健保・厚年の両方** | `services/shaho_pdf.py` |
| 関東ITSの被保険者標準報酬決定通知書 | CSV（PATPOSTで変換） | 定時決定の全員。**健保だけ** | `services/shaho_its.py` |

どちらも `PdfStatement` に揃えてから同じ `build_plan` に載せる。画面は拡張子で振り分ける。

## PDFの読み方（`services/shaho_pdf.py`）

**AIを使わない。** この帳票にはテキスト層があるので pdfplumber + 正規表現で全項目が取れる
（2026-08-17 実測で 36/36名）。確定的に読めるものに課金と非決定性を持ち込まない
（`kdx_shift_parser.py` と同じ方針。健診PDFの `health_hpm_pdf.py` は原票が画像なので別）。

1名が **3行**:

```
1073 2011001 齋藤 公伸 月額変更 第２号
73 昭55年12月06日 45 1 620 620 35,030 35,030 28,737 28,737 5,580 5,580 56,730 56,730 0 0 0 0 月額変更
( 0) 713 713
```

| 行 | 中身 |
|---|---|
| 1 | 健保№／**個人コード（=社員番号）**／氏名／改訂理由(健保)／介護区分 |
| 2 | 厚年№／生年月日／年齢／種別／**標準報酬 健保・厚年（千円単位）**／保険料6組／改訂理由(厚年) |
| 3 | (内特定保険)／子ども・子育て支援金（事業主・個人分）／２社勤務 |

保険料6組は (事業主, 個人分) の順で
**健康保険計・(健康保険)本体・(介護保険)・厚生年金・(厚生年金)基金・(厚生年金基金)**。

### 気をつけること

- **標準報酬は千円単位**。パーサの中で円に直し、以降どこでも円で扱う。
- **健保と厚年で値が違うことがある**。厚年は上限65万で頭打ち（西村稔さんは健保1150/厚年650）。
  片方だけ見て両方に入れると上限超えの人が壊れる。
- **改訂理由は2つ**（1行目=健保、2行目=厚年）。片方だけのこともある。
  9月には「定時決定」が来るので**列挙で受けず、変更・決定・改定…で終わる語**として拾う。
- 載るのは**その月に保険料が変わった人だけ**。全社員ではない。

## ★必須ガード＝2段の検算

1. **チェックサム**（`verify_totals`）— 末尾の【総合計】（人数＋保険料合計10項目）と
   読み取り結果を突き合わせ、1つでも合わなければ **ShahoPdfError で中止**。
   1行でも落としたら人数か合計が合わなくなるので、静かな取りこぼしが起きない。
2. **料率検算**（`verify_person_premiums`）
   - PDF内部の整合（マスタ不要）: 健康保険計 = 本体 + 介護 + 子ども・子育て支援金
   - 料率検算（等級表マスタ使用）: **事業主 + 個人分 = 標準報酬 × 全体料率**。
     足し合わせると端数処理が消えるので厳密に一致する。個人分だけは丸め方向が項目で違う
     （健保本体は50銭切捨てだが子育て支援金は逆に出る）ので許容差つきで見る。

値は直さない。原票が正で、ここは**読み違いを見つける網**（健診PDFのBMI検算と同じ位置づけ）。

## 関東ITSのCSVの読み方（`services/shaho_its.py`）

PATPOSTで起こした **cp932の8列CSV**。B=被保険者証番号／C=氏名／F=従前（**千円**）／
G=平均額／**H=決定標準報酬月額（円）**。H には `440 000` `1,330 000` のような
空白・カンマの崩れが入るので、数字以外を落として読む。
**適用年月がファイルに入っていない**ので、画面の「対象年月」を必須にしている。

### ★健保しか載っていない → 厚年は等級表から導く

関東ITSは健康保険組合なので H は健保の標準報酬。実測で179名中7名が厚年の上限65万を
超える（最高139万）。**厚年は `master.find_grade(H).konen_smr` で導出**し、上限に
かかる人には画面で警告を出す。179名すべてで `find_grade(H).kenpo_smr == H` が
成立することを確認済み＝H は正規の等級値。

### ★行落ち検知（A列のページ内連番）

ITS通知には社労士PDFの【総合計】のようなチェックサムが無い。代わりに
**A列（ページ内連番）が 1,2,3…と連続しているか**（ページが変わると1に戻る）で
PATPOSTの行落ちを検知し、飛び・重複・1始まりでない場合は**中止**する。
「A列は数字なのに証番号やH列が読めない行」も黙って捨てず中止する。
**限界: 各ページの最終行だけが落ちた場合は検知できない**（…18,19→次ページ1 と
…18→次ページ1 を区別できない）ので、読み取り人数を原本と目で照らすこと。
実CSV179行で誤検知なしを確認済み。テストは `SequenceTests`。

### ★本人の特定は「証番号」と「氏名」の両方（片方だけでは事故る）

jinjer側の証番号は `GET /v1/employees/social-and-labor-insurances` の
`social_insurance.health_insurance.number`。実測179名の内訳:

| 判定 | 人数 | 扱い |
|---|---|---|
| 両方一致 | 156 | 投入対象 |
| **証番号と氏名が別人を指す** | 2 | `UNRESOLVED`＝**投入させない**（承知のうえ投入も不可） |
| 証番号は一致・氏名が表記ゆれ | 3 | 投入可＋警告 |
| 氏名のみ一致（証番号が未登録） | 17 | 投入可＋警告 |
| 同じ氏名がjinjerに2件（20YYが1人） | 1 | 20YY を採る＋警告（谷津さん 2026007/3333003） |
| どちらでも決まらない | 1 | `UNRESOLVED` |

**証番号だけなら、証1151/1152 で柴田さんと岡村さんの標準報酬を入れ替えて
書き込むところだった。** 当方の定時決定計算（岡村560,000／柴田410,000）が
CSVの氏名＋H列の組み合わせと一致したので、**ずれているのは証番号の列**と分かった。
氏名だけなら Ver Martin（CSVはカタカナ）・宮嵜/宮寄・井料 香凜/香凛 を取り逃す。
同じ証番号が2人に付いていたら `load_number_map` が**どちらも捨てる**。

## 等級表とCodexの公式資料（2026-08-18 整理）

計算に使うのは **`Config.SHAHO_GRADE_TABLE_XLSX` の1本だけ**
（`Z:\API連携\標準月額資料\令和8年度_標準報酬月額表_関東IT健保_協会けんぽ東京比較.xlsx`）。
exe に値を持たないので、このファイルを差し替えれば再ビルドなしで次回から効く。

**Codex が毎月1日に `標準報酬月額_YYYY_MM.xlsx` を同じフォルダへ置く**
（上書きしない運用なので月ごとに増える）。ファイル名も中身の作りも上の等級表と
違うため**自動では読まない**。代わりに `shaho_master.find_newer_tables()` が
「設定の等級表より新しい公式資料が来ている」ことを検知し、プレビュー画面に
警告を出す（料率が変わっていれば人が等級表を差し替える）。

年度が変わったときは `load_grade_table` の年度チェックが必ず止めるので、
古い年度の料率で黙って計算することはない。この検知が拾うのは
**同じ年度のまま料率だけ改定された場合**。

## 当方計算（C）— `services/shaho_writer.py`

標準報酬モード（`shaho_engine`）の部品をそのまま使う。**算定月は改訂理由で切り替える**:

| 改訂理由 | 算定に使う3か月 | 採用条件 |
|---|---|---|
| 月額変更（随時改定） | 対象月の**直前3か月**（7月分 → 4・5・6月支給） | 3か月すべてが支払基礎日数を満たす |
| 定時決定 | その年の**4〜6月支給** | 1か月でも満たせば採用 |
| 取得時決定 | — | 見込み額なので計算しない |
| 料率変更 | — | 標準報酬は動いていない |

必要な窓は `needed_windows()` が改訂理由から決めるので、月額変更だけの紙で
定時決定の窓（前年4〜6月）を探しに行って「キャッシュが無い」と警告することはない。

## 書き込み

`JinjerWriteClient`（`services/jinjer_api_client.py`）経由のみ。基底の `JinjerClient` には
書き込みメソッドを置かない（全モードが共有しているので、気軽に呼べる場所を作らない）。

- `POST/PATCH /v1/employees/monthly-remunerations`
- body: `{employee_id, monthly_remunerations: {year, month, health_insurance:{standard_fee},
  employee_pension:{standard_fee}}}`（標準報酬月額は**円**の文字列）
- **1件25秒**（`SHAHO_IMPORT_WRITE_INTERVAL_SEC`）。社内の書き込み系スクリプトと同じ。
  詰めると429の再試行で結局遅くなる。制限は**テナント単位**なので他の投入と並走させない。

### 標準報酬が動いていない人には書かない

報酬月額は履歴テーブルで、基準年月から先に効く。**対象年月ちょうどのレコード**ではなく
**対象年月時点で有効なレコード**（対象月以前で最も新しいもの）と比べる（`pick_records`）。
ここを間違えると、料率変更だけの月に全員ぶんの履歴を足してしまう。

対象年月ちょうどのレコードが**ある → PATCH／ない → POST**。

### ⚠ 現在値のGETは月で絞らない（2026-08-17 本番exeで踏んだ）

`GET /v1/employees/monthly-remunerations` は `year`/`month` を渡すと**その月のレコードだけ**を
返す。プレビューでこれを渡していたため、**対象月にレコードが無い人が「登録なし」に見えて**
いた。有田功太郎さん（2018001）は 2026-07 のレコードが無く 2025-09 の 440,000 が効いている
状態で、PDFも 440,000＝書く必要がないのに「投入できる」に出てしまった
（先付けの 2026-09 レコード 500,000 もあり、履歴が飛び飛びなのは普通のこと）。

- **プレビューと実行直前の取り直しは、月で絞らず全履歴を取る**（`get_monthly_remunerations(emps)`）
- **投入後の検証だけは月で絞る**。絞らないと、書き込みが失敗してレコードができていない人でも
  「過去のレコードの値がたまたま同じ」で OK に見えてしまう

回帰テスト: `test_shaho_writer.test_old_record_still_counts_as_the_current_value` /
`test_future_record_is_not_treated_as_current` /
`test_app_shaho_import.test_history_is_fetched_unfiltered`。
テストのjinjer代役も**本物と同じく year/month で絞る**挙動にしてある。

### ★API投入だと徴収年月の表示が「基準年月と同じ」になる（2026-08-18 発覚・10月給与で確定させる）

**画面から入力すると徴収年月＝基準年月+1か月**になるが、
**`POST /v1/employees/monthly-remunerations` で作ると徴収年月＝基準年月と同じ**になる。
実測: 2026-09 基準のレコードのうち、画面入力の57名は徴収 2026-10、
API投入の34名は徴収 2026-09。他の1,475件はすべて「基準+1か月」。
APIのbodyに徴収年月を指定する項目は無いので、API側からは変えられない。

**谷津さんの説明（2026-08-18）**: 当社の給与は当月払いで、jinjer も当月払い用の
社保設定にしてある。**9月決定の標報が効くのは10月の給与計算**。
これが正しければ徴収年月の差は**表示だけで動作に影響しない**（＝選択肢③）。
当初ここに書いた「9月給与から早く控除される恐れ」は当月払い設定を考慮していない
心配だった可能性が高い。**34名を画面で直す必要は（今のところ）ない。**

**答え合わせの手順（これで白黒つける）**:
1. 9月給与の確定後: 経理モードでキャッシュ取得 → 標準報酬モード（突合月 2026-09）。
   API投入の34名が**旧標報のまま**控除されていれば「早く効く」恐れは消える
2. 10月給与の確定後: 突合月 2026-10 で「差異」が消える＝**新標報で控除された**ことを確認
3. 確定したら `verify_after` の徴収年月チェックを整理する（表示差と確定なら情報表示へ降格）。
   **それまでは「要確認」のまま残す**＝金額OKで徴収年月だけの要確認は想定内として扱う

### 冪等（途中で落ちたときの復旧）

**「同じPDFでもう一度プレビュー」の一本**に統一している。プレビューは毎回 jinjer の現在値を
取り直すので、投入済みの人は自動的に `NO_CHANGE` に落ち、残りだけの計画になる。
途中失敗・PC強制終了・二重実行未遂のどれでも手順は同じ。

## 画面（社労士モード内のカード）

1. `POST /shaho_import_preview` — PDFを読み、突合して計画を返す。**何も書かない**
2. `POST /shaho_import_execute`（`dry_run:true`）— 内容を確定。**何も書かない**
3. `POST /shaho_import_execute`（`dry_run:false`）— 対象年月の手入力照合を通ってから実行。
   **バックグラウンドスレッド**で走る
4. `GET /shaho_import_status` — 進捗をポーリング

**SSEにしていない理由**: 126名だと約53分かかる。SSEはブラウザのタブスリープや切断で
ジェネレータごと書き込みループが死ぬ。スレッド＋進捗ファイル（atomic書き）なら
**画面を閉じても最後まで走り、開き直せば追いつける**。

## ★給与明細キャッシュは各PCのローカルにある（トリプルチェックの前提）

C（当方計算）は `outputs/keiri/raw/salary_statements_*.json` を読む。exe は
`%LOCALAPPDATA%\KintaiChecker` で動くので、**このキャッシュは端末ごとに別物**。
経理モードを実行していない端末では計算値が1人も出せず、全員が `NO_CALC`
（＝承知のうえ投入なしで通る）になり、**トリプルチェックが2点チェックに退化する**。

2026-08-18 に実際に起きた。江成さんの端末で34名を投入したところ、
当方計算と食い違う3名（二神・中村・大村さん）がそのまま通った
（入った値は通知どおりで正しいが、確認の機会が失われた）。

対策: 算定月が1つも読めていないときは、プレビュー画面で
「この端末には給与明細キャッシュが無いため、当方の計算値を1人も出せていません」
と警告する。**急がないなら経理モードを動かしている端末で実行する。**

## 許可の2段構え（2026-08-17 谷津さん決定）

属人化を避けるため**投入そのものは管理部6名**（谷津・平良・江成・小森・山川・一戸）ができる。
3点が一致した人を入れるだけなので判断の余地がないため。
